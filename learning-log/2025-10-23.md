## Features Implemented

### 1. localStorage Conversation Persistence ✅

Added the ability to save and restore chat conversations using the browser's localStorage API.

**What is localStorage?**
- Browser API for storing data persistently on the client side
- Data survives page refreshes and browser restarts
- Stores data as strings (need JSON.stringify/parse for objects)
- ~5-10MB storage limit per domain
- Only accessible from client-side JavaScript

**Implementation:**

**A. Save Messages When They Change**
```typescript
/**
 * Save messages to localStorage whenever they change
 * This ensures conversation persists across page refreshes
 */
useEffect(() => {
  if (isMounted) {
    localStorage.setItem('chatMessages', JSON.stringify(messages));
  }
}, [messages, isMounted]);
```

**Key Learning:**
- `useEffect` with `[messages, isMounted]` dependencies runs whenever either changes
- Check `isMounted` to avoid saving during server-side rendering (Next.js)
- `JSON.stringify()` converts JavaScript objects to JSON strings for storage

**B. Load Messages on Page Load**
```typescript
useEffect(() => {
  setIsMounted(true);

  // Load saved messages from localStorage
  const savedMessages = localStorage.getItem('chatMessages');
  if (savedMessages) {
    try {
      const parsed = JSON.parse(savedMessages);
      // Convert timestamp strings back to Date objects
      const messagesWithDates = parsed.map((msg: Message) => ({
        ...msg,
        timestamp: new Date(msg.timestamp),
      }));
      setMessages(messagesWithDates);
    } catch (error) {
      console.error('Failed to load saved messages:', error);
    }
  }
}, []);
```

**Key Learning:**
- Empty dependency array `[]` means effect runs once on mount
- `JSON.parse()` converts JSON strings back to JavaScript objects
- Date objects become strings when stringified, need to convert back with `new Date()`
- Always use try/catch when parsing localStorage (data could be corrupted)

**C. Clear localStorage When Clearing Chat**
```typescript
const handleClearChat = () => {
  setMessages([
    {
      id: '1',
      text: 'Hello! How can I help you today?',
      sender: 'assistant',
      timestamp: new Date(),
    },
  ]);
  setInput('');

  // Clear saved messages from localStorage
  localStorage.removeItem('chatMessages');
};
```

**Key Learning:**
- `localStorage.removeItem()` deletes specific items
- Important to clear localStorage when user clears chat, otherwise old messages reload

## Key Debugging Lessons Learned

### 1. Systematic Debugging Approach

**The Process We Used:**
1. ✅ Verify the API/feature works in general (manual localStorage test)
2. ✅ Check if data is being saved (Application tab → Local Storage)
3. ✅ Add visible debug UI (not just console.logs)
4. ✅ Check correct deployment URL (preview vs production)
5. ✅ Inspect build configuration (package.json, turbopack)
6. ✅ Review the actual deployed code
7. ✅ Read through code line by line

**Why This Works:**
- Eliminates possibilities one by one
- Combines different debugging tools (console, UI, DevTools)
- Doesn't assume anything (verify everything)

### 2. Preview vs Production URLs on Vercel

**What We Learned:**
- **Preview URLs** change with each deployment: `project-HASH.vercel.app`
- **Production URL** stays consistent: `project.vercel.app`
- Always check which URL you're testing!
- Bookmark the production URL for consistency

### 3. Console.logs May Not Show in Production

**Why:**
- Production builds often strip console.logs for performance
- Minification/optimization can remove debug code
- Better to use visible UI elements for critical debugging

**Better Debugging Techniques:**
- Add temporary UI elements (like our debug text)
- Use browser DevTools (Network, Application tabs)
- Check actual behavior, not just logs

### 4. Turbopack Considerations

**What is Turbopack?**
- Next.js's new bundler (experimental)
- Supposed to be faster than Webpack
- Still has some edge cases and bugs

**Our Experience:**
- Removed `--turbopack` from build script
- Reverted to standard Next.js compiler
- More stable and battle-tested

**Lesson:** Avoid experimental features in production until they're stable.

### 5. Always Review Code Before Deploying

**What Happened:**
- We commented out code during debugging
- Forgot to uncomment it
- Deployed broken code to production

**Prevention:**
- Review git diff before committing
- Test locally before deploying
- Keep a checklist of temporary debug code to remove

## TypeScript Concepts Learned

### 1. useEffect Dependency Arrays

**How Dependencies Work:**
```typescript
// Run once on mount
useEffect(() => {
  // code
}, []);

// Run when `messages` or `isMounted` changes
useEffect(() => {
  // code
}, [messages, isMounted]);

// Run on every render (usually bad!)
useEffect(() => {
  // code
});
```

**Key Rules:**
- Empty array `[]` = run once on component mount
- Array with values = run when those values change
- No array = run on every render (usually causes infinite loops!)
- React compares values with `Object.is()` (reference equality)

### 2. Type Assertions in map()

**The Problem:**
```typescript
const parsed = JSON.parse(savedMessages);  // Type: any
const messagesWithDates = parsed.map((msg: Message) => ({
  ...msg,
  timestamp: new Date(msg.timestamp),
}));
```

**Why `msg: Message` instead of `msg: any`?**
- TypeScript doesn't know what `JSON.parse()` returns (could be anything)
- We know it's an array of `Message` objects
- Using `msg: Message` gives us type safety and autocomplete
- Better than `any` which disables type checking

**Alternative (type assertion on parsed):**
```typescript
const parsed = JSON.parse(savedMessages) as Message[];
```

Both approaches work, but inline type annotation in map is more explicit.

### 3. Conditional className with Template Literals

**Pattern:**
```typescript
className={`base-classes ${condition ? 'true-classes' : 'false-classes'}`}
```

**Example:**
```typescript
className={`px-6 py-2 rounded-lg transition-colors font-medium ${
  isLoading
    ? 'bg-gray-400 text-gray-200 cursor-not-allowed'
    : 'bg-blue-500 text-white hover:bg-blue-600'
}`}
```

**How It Works:**
- Template literals (backticks) allow embedded expressions `${...}`
- Ternary operator: `condition ? ifTrue : ifFalse`
- Results in one string with all classes combined
- Base classes always apply, conditional classes swap based on state

### 4. Spread Operator with Objects

**Pattern:**
```typescript
const messagesWithDates = parsed.map((msg: Message) => ({
  ...msg,
  timestamp: new Date(msg.timestamp),
}));
```

**What `...msg` does:**
- Spreads all properties of `msg` into the new object
- Then we override the `timestamp` property
- Creates a new object (doesn't mutate original)

**Equivalent to:**
```typescript
{
  id: msg.id,
  text: msg.text,
  sender: msg.sender,
  timestamp: new Date(msg.timestamp),  // Override this one
  sources: msg.sources,
}
```

**Much cleaner than writing out all properties!**

## React Patterns Learned

### 1. The `isMounted` Pattern

**Why We Need It:**
- Next.js renders components on server first (SSR)
- localStorage only exists in the browser (not on server)
- Calling `localStorage` during SSR causes errors

**The Solution:**
```typescript
const [isMounted, setIsMounted] = useState(false);

useEffect(() => {
  setIsMounted(true);  // Now we know we're on client

  // Safe to use localStorage here
  const saved = localStorage.getItem('key');
}, []);

// In another useEffect
useEffect(() => {
  if (isMounted) {
    // Only save when client-side
    localStorage.setItem('key', value);
  }
}, [value, isMounted]);
```

**How It Works:**
1. Component renders on server with `isMounted = false`
2. Component hydrates on client
3. useEffect runs (only on client), sets `isMounted = true`
4. Other effects can now safely use browser APIs

**Alternative:** Could use a library like `react-use` with `useLocalStorage` hook

### 2. Saving State on Every Change

**Pattern:**
```typescript
const [data, setData] = useState(initialValue);

// Save to localStorage whenever data changes
useEffect(() => {
  if (isMounted) {
    localStorage.setItem('key', JSON.stringify(data));
  }
}, [data, isMounted]);
```

**Pros:**
- Simple and automatic
- Never lose data
- No need to remember to save manually

**Cons:**
- Runs on every state change (could be frequent)
- For large datasets, could impact performance

**For Our Use Case:**
- Perfect! Messages don't change that often
- Array is small (typically <50 messages)
- Performance impact negligible

### 3. Loading from localStorage Before Rendering

**Timing is Important:**
```typescript
useEffect(() => {
  setIsMounted(true);

  const saved = localStorage.getItem('chatMessages');
  if (saved) {
    setMessages(JSON.parse(saved));  // Load before user sees anything
  }
}, []);  // Empty array = runs once immediately on mount
```

**Why Empty Dependency Array:**
- We only want to load once
- Loading on every render would be wasteful
- User should see saved messages immediately

### Challenge 4: Deciding When to Use localStorage vs Database

**Question:** Why use localStorage instead of saving to a database?

**localStorage Pros:**
- ✅ No backend required
- ✅ Instant (no network latency)
- ✅ Works offline
- ✅ Free (no database costs)
- ✅ Simple to implement

**localStorage Cons:**
- ❌ Only persists on one browser/device
- ❌ User can clear it
- ❌ Limited storage (5-10MB)
- ❌ No sync across devices

**Database Pros:**
- ✅ Syncs across devices
- ✅ Persistent (user can't accidentally clear)
- ✅ Unlimited storage
- ✅ Can implement sharing/collaboration

**Database Cons:**
- ❌ Requires backend/authentication
- ❌ Network latency
- ❌ Costs money (hosting)
- ❌ More complex

**Our Decision:**
- Use localStorage for now (MVP)
- Good enough for single-device use
- Can migrate to database later
- Shows understanding of both approaches in interviews

**Future Enhancement:**
- Add authentication (Clerk/Auth0)
- Save conversations to PostgreSQL
- Sync across devices
- Keep localStorage as cache for offline use

## What I Learned About localStorage

### localStorage Basics

**Storage API Methods:**
```javascript
// Save
localStorage.setItem(key, value);

// Get
localStorage.getItem(key);  // Returns null if not found

// Remove
localStorage.removeItem(key);

// Clear all
localStorage.clear();

// Get number of items
localStorage.length;

// Get key by index
localStorage.key(0);
```

### Working with Objects

**Must stringify/parse:**
```javascript
// ❌ Wrong - stores "[object Object]"
localStorage.setItem('data', {name: 'test'});

// ✅ Correct - stringify first
localStorage.setItem('data', JSON.stringify({name: 'test'}));

// ✅ Parse when retrieving
const data = JSON.parse(localStorage.getItem('data'));
```

### Handling Date Objects

**Dates become strings when stringified:**
```javascript
const message = {
  text: 'Hello',
  timestamp: new Date(),
};

// Save
localStorage.setItem('msg', JSON.stringify(message));

// Load - timestamp is now a string!
const loaded = JSON.parse(localStorage.getItem('msg'));
console.log(typeof loaded.timestamp);  // "string"

// Need to convert back
loaded.timestamp = new Date(loaded.timestamp);
console.log(typeof loaded.timestamp);  // "object" (Date)
```

### Storage Limits

**Typical limits:**
- **5-10MB** per domain (varies by browser)
- Synchronous API (blocks main thread)
- Strings only (no binary data)

**Testing limit:**
```javascript
try {
  localStorage.setItem('test', 'x'.repeat(10000000));  // 10MB
} catch (e) {
  console.error('Storage full!', e);
}
```

### Security Considerations

**What localStorage CAN'T protect against:**
- ❌ XSS attacks (JavaScript can access localStorage)
- ❌ User can clear it manually
- ❌ No encryption (data stored in plain text)
- ❌ Same-origin policy (can't access other domains' storage)

**Best Practices:**
- ✅ Don't store sensitive data (passwords, credit cards)
- ✅ Don't store API keys or tokens (use httpOnly cookies instead)
- ✅ Validate/sanitize data before using it
- ✅ Handle localStorage being unavailable (private browsing)

**Our Use Case is Perfect:**
- Just storing chat messages
- No sensitive data
- User owns the data
- Clearing it is acceptable
