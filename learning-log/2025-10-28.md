## TypeScript/Python Concepts Learned

### 1. Rate Limiting with slowapi
**What it is:** A library that prevents API abuse by limiting how many requests a user can make in a time window.

**Why we need it:**
- Protects Groq API quota (free tier has limits)
- Prevents malicious users from overloading server
- Ensures fair usage across all users

**Implementation:**
```python
from slowapi import Limiter, _rate_limit_exceeded_handler
from slowapi.util import get_remote_address
from slowapi.errors import RateLimitExceeded

# Initialize rate limiter - tracks requests by IP address
limiter = Limiter(key_func=get_remote_address)

# Add to FastAPI app
app.state.limiter = limiter

# Apply to endpoint
@app.post("/chat")
@limiter.limit("10/minute")  # Max 10 requests per minute
async def chat(request: Request, query: QueryRequest):
    # ... endpoint logic
```

**Key Concepts:**
- `key_func=get_remote_address` - Tracks requests by IP address
- `"10/minute"` - Rate limit format: `{number}/{time_unit}`
- Decorator order matters: `@limiter.limit()` goes AFTER `@app.post()`

### 2. Custom Exception Handlers in FastAPI
**What it is:** Functions that run when specific errors occur, allowing custom responses and logging.

**Pattern:**
```python
@app.exception_handler(RateLimitExceeded)
async def rate_limit_handler(request: Request, exc: RateLimitExceeded):
    # Custom logging
    logger.warning(f"Rate limit exceeded for IP: {request.client.host}")

    # Return default rate limit response
    return _rate_limit_exceeded_handler(request, exc)
```

**Why This is Useful:**
- ✅ Log when rate limits are hit (track abusive users)
- ✅ Customize error response format
- ✅ Add additional context (IP address, timestamp)
- ✅ Can send alerts/notifications on repeated violations

### 3. Structured Logging in Python
**What it is:** Organized logging with consistent format for tracking application events.

**Setup:**
```python
import logging
import sys

logging.basicConfig(
    level=logging.INFO,  # Log INFO and above (INFO, WARNING, ERROR, CRITICAL)
    format='%(asctime)s - %(name)s - %(levelname)s - %(message)s',
    handlers=[
        logging.StreamHandler(sys.stdout)  # Output to console
    ]
)

logger = logging.getLogger("kb-rag-api")
```

**Log Levels:**
- `DEBUG` - Detailed information for debugging
- `INFO` - General information (server started, request received)
- `WARNING` - Something unexpected but not critical (rate limit hit)
- `ERROR` - Serious problem (database error, API failure)
- `CRITICAL` - System failure (database down, out of memory)

**Usage in Code:**
```python
# Warning - something unusual but expected
logger.warning(f"Rate limit exceeded for IP: {request.client.host}")

# Error - something broke, includes full stack trace
logger.error(f"Error in chat endpoint: {str(e)}", exc_info=True)
```

**Why `exc_info=True` is Important:**
- Includes full exception stack trace
- Shows exactly which line caused the error
- Essential for debugging production issues

### 4. Database Transaction Rollback
**What it is:** Reverting database changes when an error occurs to maintain data integrity.

**Problem Without Rollback:**
```python
# Bad - if commit fails, partial data might be saved
db_conversation = Conversation(user_id=user_id, messages=messages)
db.add(db_conversation)
db.commit()  # If this fails, db.add() changes might persist
```

**Solution - Rollback on Error:**
```python
try:
    db_conversation = Conversation(user_id=user_id, messages=messages)
    db.add(db_conversation)
    db.commit()  # Save to database
    db.refresh(db_conversation)  # Load the saved data
    return db_conversation
except Exception as e:
    logger.error(f"Error creating conversation: {str(e)}", exc_info=True)
    db.rollback()  # Undo any changes
    raise HTTPException(status_code=500, detail="Failed to save conversation")
```

**Why This Matters:**
- Prevents partial/corrupted data in database
- Ensures database stays consistent (all changes succeed or all fail)
- Standard practice for ACID transactions

### 5. Re-raising Exceptions in Python
**Pattern:** Catching an exception, handling it, then raising it again.

**Why We Do This:**
```python
try:
    db_conversation = db.query(Conversation).filter(...).first()

    if not db_conversation:
        raise HTTPException(status_code=404, detail="Conversation not found")

    # ... update logic ...
    db.commit()
    return db_conversation
except HTTPException:
    raise  # Re-raise 404 errors without logging
except Exception as e:
    logger.error(f"Error updating conversation: {str(e)}", exc_info=True)
    db.rollback()
    raise HTTPException(status_code=500, detail="Failed to update conversation")
```

**Explanation:**
- `HTTPException` (404) = Expected error (user requested non-existent conversation)
- `Exception` (anything else) = Unexpected error (database failure, network issue)
- We re-raise HTTPException without logging because 404 is normal behavior
- Only log unexpected errors (database failures, bugs)

**Key Learning:** Not all errors are bad! Expected errors (404, 401) shouldn't clutter logs.

### 6. Parameter Naming Conflicts in FastAPI
**Problem We Hit:**
```python
# ❌ This caused an error
@app.post("/chat")
@limiter.limit("10/minute")
async def chat(request: QueryRequest):  # Wrong type
    # slowapi expects parameter named 'request' of type Request
```

**Error Message:**
```
Exception: parameter 'request' must be an instance of starlette.requests.Request
```

**Solution:**
```python
# ✅ Fixed - both parameters present
@app.post("/chat")
@limiter.limit("10/minute")
async def chat(request: Request, query: QueryRequest):
    # slowapi finds 'request: Request'
    # We use 'query.query' for the user's question
```

**Lesson:**
- Decorators can require specific parameter names/types
- Read decorator documentation carefully
- When you get parameter type errors, check what the decorator expects

### 7. TypeScript Error Handling - Specific Messages
**Before (vague):**
```typescript
if (response.status === 429) {
    throw new Error("You're sending too many messages. Please wait a moment.");
}
```

**After (specific):**
```typescript
if (response.status === 429) {
    throw new Error("You've sent too many messages. Please wait 1 minute and try again.");
}
```

**Key Learning:** User-facing error messages should be:
- **Specific** - Tell them exactly how long to wait
- **Actionable** - Tell them what to do next
- **Polite** - Don't sound accusatory ("You've sent" not "You're spamming")

## Challenges Faced

### Challenge 1: Parameter Naming Conflict
**Problem:** Got error `parameter 'request' must be an instance of starlette.requests.Request`

**Cause:** slowapi decorator looks for a parameter named `request` with type `Request`, but we used that name for our `QueryRequest` parameter.

**Debugging Process:**
1. Read error message - it wants `starlette.requests.Request`
2. Checked slowapi documentation - requires `Request` parameter
3. Initial attempt: renamed to `req: Request` - didn't work (slowapi still looked for `request`)
4. Solution: Keep both parameters - `request: Request, query: QueryRequest`

**Lesson:** Some decorators require specific parameter names. When you get type errors, check what the decorator/middleware expects.

### Challenge 2: Vague Error Messages
**Problem:** Initial rate limit error said "wait a moment" - too vague.

**User Feedback:** "I feel that the error message is vague for the user. making it specify something like wait for 1 min would be helpful?"

**Solution:** Changed to "Please wait 1 minute and try again."

**Lesson:**
- Always be specific in user-facing messages
- Tell users exactly what to do and how long it takes
- Test error messages from user's perspective - does it answer their questions?

### Challenge 3: Testing Rate Limit in UI
**Problem:** It's hard to send 10 messages in 1 minute naturally to test the error UI.

**Solution:**
- Tested with curl (easy to send 11 requests quickly)
- Verified backend returns 429 error correctly
- Verified frontend error handling code is correct
- Decided not to manually test in UI since mechanism is proven

**Lesson:**
- Not all features need manual UI testing
- If you can verify the mechanism works (curl test) and code is correct (code review), that's sufficient
- Focus testing effort on areas with most uncertainty

### Challenge 4: When to Log Errors
**Problem:** Should we log all exceptions, including 404 errors?

**Answer:** No! Distinguish between expected and unexpected errors.

**Expected Errors (don't log as errors):**
- 404 - User requested non-existent resource
- 401 - User not authenticated
- 400 - Bad request (validation failed)

**Unexpected Errors (log with stack trace):**
- 500 - Database failure, network error, bugs
- API failures (Groq, PostgreSQL down)

**Implementation:**
```python
try:
    # ... logic ...
    if not found:
        raise HTTPException(status_code=404, detail="Not found")
except HTTPException:
    raise  # Re-raise without logging
except Exception as e:
    logger.error(f"Unexpected error: {str(e)}", exc_info=True)
    raise HTTPException(status_code=500, detail="Server error")
```

**Lesson:** Good logging is about signal-to-noise ratio. Only log unexpected problems.

## Production-Ready Patterns Learned

### 1. Rate Limiting Pattern
```python
# Always rate limit public endpoints to prevent abuse
@app.post("/chat")
@limiter.limit("10/minute")
async def chat(request: Request, query: QueryRequest):
    # ... endpoint logic
```

**When to Use:**
- Public APIs (no authentication)
- Expensive operations (LLM calls, database queries)
- Endpoints that could be abused

**Common Limits:**
- Chat/LLM endpoints: 10-20 requests/minute
- Authentication: 5 requests/minute (prevent brute force)
- Search: 30-60 requests/minute
- Read-only endpoints: 100+ requests/minute

### 2. Error Logging Pattern
```python
try:
    # Business logic
    result = expensive_operation()
    return result
except Exception as e:
    # Log with context
    logger.error(f"Error in {operation_name}: {str(e)}", exc_info=True)
    # Return user-friendly error
    raise HTTPException(status_code=500, detail="An error occurred")
```

**Key Elements:**
- Include context in log message (user_id, conversation_id, operation)
- Use `exc_info=True` for stack trace
- Return generic message to user (don't expose internal details)

### 3. Database Transaction Pattern
```python
try:
    # Database operations
    db.add(item)
    db.commit()
    db.refresh(item)
    return item
except Exception as e:
    logger.error(f"Database error: {str(e)}", exc_info=True)
    db.rollback()  # Critical - undo changes
    raise HTTPException(status_code=500, detail="Failed to save")
```

**Why This Pattern:**
- Ensures data consistency
- Prevents partial saves
- Standard in production applications

### 4. Re-raise Exception Pattern
```python
try:
    # Logic that might raise HTTPException
    if not found:
        raise HTTPException(status_code=404)
    # ... other logic that might fail ...
except HTTPException:
    raise  # Re-raise without logging (expected error)
except Exception as e:
    logger.error(f"Unexpected error: {str(e)}", exc_info=True)
    db.rollback()
    raise HTTPException(status_code=500)
```

**Why This Pattern:**
- Separates expected errors (404) from unexpected (500)
- Prevents log clutter with normal user behavior
- Easier to find real bugs in production logs

## Key Takeaways

### 1. Rate Limiting is Essential for Production
Without rate limiting:
- ❌ Malicious users can abuse your API
- ❌ Your Groq API quota can be exhausted
- ❌ Server can be overloaded

With rate limiting:
- ✅ Fair usage across all users
- ✅ Protected API quotas
- ✅ Server stays responsive

**Lesson:** Always add rate limiting to public endpoints before deploying to production.

### 2. Good Logging Makes Debugging Easier
When errors happen in production, logs are your only window into what went wrong.

**Good log message:**
```python
logger.error(f"Error creating conversation for user {user_id}: {str(e)}", exc_info=True)
```
- Includes context (user_id)
- Describes what was happening (creating conversation)
- Includes stack trace (exc_info=True)

**Bad log message:**
```python
logger.error("Error occurred")  # Which error? Where? For which user?
```

**Lesson:** Include context in log messages. Future you will be grateful!

### 3. Not All Errors Are Equal
**Expected Errors (normal behavior):**
- User requests non-existent conversation → 404
- User not authenticated → 401
- Invalid input → 400

**Unexpected Errors (bugs/failures):**
- Database connection lost → 500
- LLM API failed → 500
- Code threw exception → 500

**Lesson:** Only log unexpected errors. Expected errors are part of normal operation.

### 4. Be Specific in Error Messages
Users don't understand technical jargon. Error messages should:
- ✅ Explain what happened in simple terms
- ✅ Tell them what to do next
- ✅ Be specific (not vague)

**Bad:** "An error occurred. Please try again."
**Good:** "You've sent too many messages. Please wait 1 minute and try again."

**Lesson:** Write error messages from the user's perspective.

### 5. Database Transactions Need Rollback
When database operations fail, you MUST rollback to prevent data corruption.

**Without Rollback:**
- Partial data might be saved
- Database in inconsistent state
- Hard to debug issues

**With Rollback:**
- All-or-nothing (either all changes succeed or none do)
- Database stays consistent
- Easy to understand what happened

**Lesson:** Always use try-except with `db.rollback()` for database operations.

### 6. Test the Mechanism, Not Just the UI
We tested rate limiting with curl instead of manually in the UI. This was:
- ✅ Faster (11 requests in 1 second vs 1 minute of clicking)
- ✅ More reliable (exact timing, consistent conditions)
- ✅ Easier to automate (can add to test suite later)

**Lesson:** Use the right tool for testing. curl/pytest for backend, browser for UI.

### 7. Read Documentation When Using New Libraries
slowapi required a specific parameter name (`request: Request`). We found this by:
1. Reading the error message
2. Checking slowapi documentation
3. Looking at example code

**Lesson:** When using a new library, always check the docs for required patterns.
