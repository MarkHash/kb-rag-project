**What is Railway?**

**Steps We Took:**

**A. Created `requirements.txt`**
```txt

**Key Learning:** Use CPU-only PyTorch for cloud deployment to avoid timeouts from downloading 3GB+ CUDA packages.

**B. Created `Procfile`**
```

**What this does:**
- Tells Railway how to start the app
- `--host 0.0.0.0` = Listen on all network interfaces (required for cloud)
- `--port $PORT` = Use Railway's assigned port (Railway sets this automatically)

**F. Deployed to Railway**

### 2. Debugging Dependency Hell 🔥

Hit multiple dependency compatibility issues during deployment. Here's what broke and how we fixed it:

**Error 1: Build Timeout**
- **Problem:** PyTorch was downloading 3GB+ CUDA packages
- **Solution:** Used CPU-only PyTorch with `--extra-index-url https://download.pytorch.org/whl/cpu`

**Error 2: NumPy 2.0 Incompatibility**
```
AttributeError: 'np.float_' was removed in the NumPy 2.0 release
```
- **Problem:** ChromaDB 0.4.18 incompatible with NumPy 2.0
- **Solution:** Added `numpy<2.0` to requirements.txt

**Error 3: sentence-transformers Too Old**
```
ImportError: cannot import name 'cached_download' from 'huggingface_hub'
```
- **Problem:** sentence-transformers 2.2.2 incompatible with newer huggingface_hub
- **Solution:** Upgraded to sentence-transformers 3.3.1

**Error 4: Groq API Client Incompatibility**
```
TypeError: Client.__init__() got an unexpected keyword argument 'proxies'
```
- **Problem:** groq 0.4.1 incompatible with newer httpx
- **Solution:** Upgraded to groq 0.13.0

**Key Takeaway:** Cloud deployment reveals dependency issues that don't show up locally. Always test deploy early!

### 4. Fixing CORS Issues 🔒

**The Problem:**
```
INFO: 100.64.0.4:37700 - "OPTIONS /chat HTTP/1.1" 400 Bad Request
```

Frontend was blocked from calling backend due to CORS (Cross-Origin Resource Sharing) restrictions.

**What is CORS?**
- Browser security feature that blocks requests between different domains
- Frontend (vercel.app) and backend (railway.app) are different origins
- Backend must explicitly allow the frontend's origin

**Initial (Broken) Configuration:**
```python
allow_origins=[
    "http://localhost:3000",
    "https://*.vercel.app",  # ❌ Wildcards don't work!
]
```

**Fixed Configuration:**
```python
allow_origins=[
    "http://localhost:3000",
    "https://kb-rag-project-lh7cyx8y9-mark-hashimotos-projects.vercel.app",
    "https://kb-rag-project.vercel.app",
]
```

**Key Learning:** FastAPI's CORSMiddleware does exact string matching. Wildcards like `*.vercel.app` don't work - you must specify exact URLs.

## TypeScript Concepts Learned

### 1. Environment Variables in Next.js

**Client-side variables must have `NEXT_PUBLIC_` prefix:**
```typescript
// ✅ Works in browser
const API_URL = process.env.NEXT_PUBLIC_API_URL;

// ❌ Returns undefined in browser (only works server-side)
const API_URL = process.env.API_URL;
```

**Why?** Security! Prevents accidentally exposing server secrets to the browser.

### 2. Optional Chaining with Environment Variables

```typescript
const API_BASE_URL = process.env.NEXT_PUBLIC_API_URL || 'http://localhost:8000';
```

**What this does:**
- If `NEXT_PUBLIC_API_URL` is set → use it
- If not set or empty → fallback to localhost
- Ensures app works in both development and production

## Challenges Faced & Solutions

### Challenge 1: Railway Deployment Timeout
**Problem:** Initial deployment took >10 minutes and timed out downloading PyTorch CUDA packages.

**How We Debugged:**
- Checked Railway build logs in browser
- Saw packages like `torch-2.9.0+cu121` (CUDA version)
- Realized we don't need GPU support in cloud

**Solution:**
- Used CPU-only PyTorch with special index URL
- Reduced build from 10+ minutes to ~2 minutes

**Lesson:** Optimize dependencies for cloud environment (no GPU = use CPU versions)

---

### Challenge 2: GROQ_API_KEY Not Found
**Problem:** Environment variable set during service creation didn't persist.

**Error:**
```
groq.GroqError: The api_key client option must be set
```

**How We Debugged:**
- Checked Railway logs for error message
- Ran `railway variables` to list all variables
- Found no variables set!

**Solution:**
- Link to service first: `railway service`
- Set variable: `railway variables --set GROQ_API_KEY=...`

**Lesson:** Always verify environment variables are actually set in cloud platform.

---

### Challenge 3: CORS Blocking Frontend Requests
**Problem:** Vercel frontend couldn't call Railway backend despite correct API URL.

**Error in Railway logs:**
```
INFO: 100.64.0.4:37700 - "OPTIONS /chat HTTP/1.1" 400 Bad Request
```

**How We Debugged:**
1. **Browser Console:** Saw "Failed to fetch" error
2. **Network Tab:** Saw OPTIONS request failing with 400
3. **Railway Logs:** Confirmed OPTIONS 400 (CORS preflight failed)
4. **Recognized pattern:** OPTIONS 400 = CORS configuration issue

**Solution:**
- Updated `allow_origins` in `main.py` with exact Vercel URL
- Redeployed backend with `railway up`
- Tested again → SUCCESS!

**Lesson:** CORS requires exact origin URLs. Always check backend logs + browser console together.

## Troubleshooting Techniques Learned

### The Debugging Flow for Deployment Issues

**1. Browser Console First**
- Open Dev Tools (F12) → Console tab
- Look for error messages
- Check Network tab for failed requests

**2. Backend Logs Next**
```bash
railway logs
railway logs --follow  # Real-time
```
- Look for status codes (200 = success, 400 = bad request, 500 = server error)
- Pattern: OPTIONS 200 + POST 200 = Working
- Pattern: OPTIONS 400 = CORS issue

**3. Test API Directly (Bypass Browser)**
```bash
curl https://backend-url.railway.app/chat -X POST \
  -H "Content-Type: application/json" \
  -d '{"query": "test"}'
```
- If curl works but browser doesn't → CORS issue
- If curl also fails → Backend problem

**4. Check Environment Variables**
```bash
# Backend
railway variables

# Frontend (check .env.local exists)
cat frontend/.env.local

# Remember: Restart dev server after .env changes!
```

**5. Verify Configuration**
- CORS origins list
- API URLs match
- Environment variable names correct (especially `NEXT_PUBLIC_` prefix!)

**Key Insight:** Always check browser console + backend logs TOGETHER. The combination tells you exactly where the problem is.

## Key Takeaways

### 1. Cloud Deployment is Different from Local Development
- Dependencies that work locally may fail in cloud (CUDA, NumPy versions)
- Environment variables must be explicitly set in cloud platforms
- Always test deploy early to catch issues

### 2. CORS is Essential for Full-Stack Apps
- Frontend and backend on different domains = CORS required
- Must specify exact origin URLs (wildcards don't work in FastAPI)
- OPTIONS request = CORS preflight check (browser asking "Is this allowed?")

### 3. Git Preserves ALL History
- Branches are just labels, commits are permanent
- Merging updates current code but keeps all old versions
- Can always go back to any previous commit
- Safe to delete branches after merging

### 4. Environment Variables Have Different Scopes
- **Next.js:** `NEXT_PUBLIC_*` for browser, regular for server-only
- **Railway:** Set in dashboard or CLI, available to backend
- **Local:** `.env` or `.env.local` (never commit these!)

### 5. Systematic Debugging Wins
- Browser console + backend logs = complete picture
- Test API directly with curl to isolate CORS vs backend issues
- Check environment variables are actually set
- Read error messages carefully (they often tell you exactly what's wrong!)
